# Rule-Derived Test Design — 思想

作業用ドキュメント。日本語で書き、**Ruledger が形になった時点で消す。** 読者は証明と体験を
Ruledger から受け取るのであって、この文書を読むのではない。残すべきものは README が引き取る。
方式を **Rule-Derived Test Design (RDTD)**、それを Rulealize の上で実装した道具を
**Ruledger** と呼ぶ。原体験は [motivation.md](motivation.md)。

## 決定済み事項

2026-09-19 時点。以降の執筆はこれを前提とする。

| 層 | 内容 |
|---|---|
| **価値** | 一部の人の才能でインシデントを回避しなきゃならない開発は間違っている |
| **中心主張** | テスト設計を作る工数は機械に移る。人に残るのは、機械の選び方を変えることと、出された設計が意図どおりかの確認である |
| **根拠** | ルールセットについて観測できることは有限で、すべて機械が集められる。合法な入力の集合、終局と `Result`、遷移先 |
| **基盤** | RDTD は Rulealize を前提とする。汎用言語には適用しない |
| **道具** | Ruledger は状態を歩いて集め、各状態で観測できることを全部書き出す。人は機械の選び方を変えたいときだけ手を入れる |
| **設計原則** | 解釈を加えない。出力はルールセットと同義である。トートロジーは忠実さの保証であって欠陥ではない |
| **オラクル** | 人の意図。システムの外にある。機械は正しさを判定しない |
| **v1 の範囲** | テスト設計の出力と、その差分と、人が入れた編集の持ち越しまで。承認記録は持たない。編集済みの設計はリポジトリにコミットする |

補足として確定していること。

- **新語を作らない。** 固有名詞は Ruledger と Rulealize のみ。`galley` / `grain` は取り下げ済み。
  それぞれ「テスト設計」「粒度」で足りる。
- **名前。** 方式は **Rule-Derived Test Design (RDTD)**、道具は **Ruledger**。2026-09-20 確定。
  方式名は普通名詞の連なりであり、語彙を増やさない。道具名は Rulealize と同じ作りの固有名詞で、
  記帳する道具であることを述べる。判定はしない (§4.4)。
- **AI は前提にしない。** 思想は AI 以前から成立している。AI は問題を加速させた一要因として
  付録で触れるに留める。

## 1. 問題 — なぜ品質が才能に依存するのか

### 1.1 一行のコードが、要求より多くを決めている

要求はこうである。**「パスワードは 8 文字以上とする」**

実装はこうなる。

```csharp
if (password.Length < 8) return Error.TooShort;
```

この一行は要求を満たしている。そして同時に、四つのことを決めている。そのうち三つは、
要求が何も言っていないことである。

| 判断 | 要求は何と言っているか |
|---|---|
| 8 文字未満を拒否する | **決めている** |
| 前後の空白を除去せずに数える | 何も言っていない |
| 絵文字や結合文字を何文字と数えるか | 何も言っていない |
| 文字数の上限を設けない | 何も言っていない |

`"👨‍👩‍👧‍👦"` は、この実装では 11 文字である。絵文字四つと、それらを繋ぐ結合子三つが、
そう数えられる。要求を書いた人間が、家族の絵文字ひとつをパスワードとして通すことを
意図した瞬間は一度もない。

実装者は四つすべてに答えを出した。出さなければコードが動かないからである。
そして四つは、同じ一行の中に同居している。

**そしてこの四つが並んだ一覧は、どこにも存在しない。**

作ることはできる。型で表現する、要求 ID を添えた表明を置く、注釈を書く、テスト設計書に
書き出す。手段がないわけではない。だが、どれも義務ではない。そして決定的なのは、
**書き残せるのは気づいた判断だけである** ということだ。気づかなかった判断は、
一覧から漏れるのではなく、一覧の対象にすらならない。

これは実装者が手を抜いた結果ではない。要求が有限の文で書かれ、実装が動作する機械で
ある以上、実装は必ず要求より多くを決める。この差は埋まらない。

そして、これは文字コードの話ではない。例に `.Length` を選んだのは一行で済むからで
あって、同じ構造は要求と実装のあらゆる対に現れる。「一覧を新着順で表示する」は、
投稿時刻が同じ二件の順序を決めていない。「上司の承認が必要である」は、上司が既に
退職している場合を決めていない。要求が有限の文であるかぎり、実装はその文が触れて
いない領域を必ず埋める。

### 1.2 一覧がないなら、全部読むか、勘で選ぶしかない

テスト設計者が要求仕様書だけを読んで書けるのは、表の一行目である。
二行目以降は、実装を読み込んで初めて現れる。

取れる手は二つしかない。

- **実装の全行を読み、含まれるすべての判断を洗い出す。** 網羅的だが、現実の規模では
  破綻する。そして読み落としたかどうかを確かめる方法がない。
- **経験と勘で、危なそうな箇所を選ぶ。** 実行可能だが、選べる範囲は選ぶ人の能力で決まる。

現場が採っているのは後者である。そして後者を高い精度でこなせる人が、
「QA センスのある人」と呼ばれている。

### 1.3 才能に依存した品質は、担保ではなく賭けである

「あの人がレビューに入ると障害が減る」——これは称賛として語られる。
だが内容は、組織が抱えている欠陥の報告である。

才能には三つの性質がある。

- **再現しない。** 同じ人でも、疲れていれば見落とす。
- **スケールしない。** 人数を倍にしても、勘のある人が倍になるわけではない。
- **退職する。** 品質はその日を境に下がり、誰も原因を特定できない。

才能が属人的であること自体は、それだけでは欠陥ではない。設計もレビューも属人的である。
問題は、品質保証が **属人性を許されない種類の仕事** だという点にある。

会計監査が担当者の勘に依存していれば、それは監査と呼べない。投薬前の照合が看護師の
記憶力に依存していれば、それは照合と呼べない。どちらの分野でも、検証の工程が個人の
資質に左右される状態は欠陥として扱われ、手順と記録に置き換えられてきた。
ソフトウェアのテストだけが、この置き換えを済ませていない。

担保とは、結果が保証されていることをいう。賭けとは、結果が確率的であることをいう。
インシデントの回避が個人の資質に依存しているとき、そこにあるのは後者である。
担保しているように見えていただけで、実際には特定の個人に賭けている。

さらに悪いのは、この構造が **責任の所在を歪める** ことである。事故が起きたとき、
問われるのは「なぜ気づけなかったのか」になる。気づけるかどうかが才能の問題である以上、
この問いに答えはない。にもかかわらず、問われるのは常に人である。

### 1.4 カバレッジは、書かれなかったテストを見ない

カバレッジは「テストがコードのどこを通ったか」を測る。

1.1 の一行は、8 文字未満のケースを一つ書けば分岐カバレッジ 100% に達する。
絵文字をどう数えるかは、誰も確認していない。それでもカバレッジは満点である。

これは測り方が甘いのではない。**測っている対象が違う。** カバレッジが数えるのは、
**書かれたテストが通った範囲** である。書かれなかったテストは視野に入らない。
洗い出しが漏れていれば、漏れたまま満点になる。

どれだけ精度を上げても同じである。分岐カバレッジを条件カバレッジにしても、数える
対象が「書かれたテスト」であるかぎり、**書かれなかったものは見えない。**

そして、より良い指標を作れば済む話でもない。**漏れは、定義上、数えられない。**
洗い出せなかったケースは、洗い出せなかったという事実ごと存在しないので、
どんな数え方をしても分母に入らない。数えられないものを数える指標は作れない。

問題は数字の精度ではなかった。**数字で品質を代理しようとしたこと** である。
この節の結論は、より良い指標の提案ではない。**指標では解決しない** ということである。

### 1.5 解くべきは一点である

1. 実装は、要求が書いた以上のことを決めている。
2. **実装が決めたことの一覧は、どこにも存在しない。**
3. 一覧がないので、人は実装を読んで洗い出すしかない。そして洗い出せたかどうかを
   確かめる方法もない。
4. その結果、品質は個人の才能に依存する。才能は再現せず、スケールせず、退職する。
5. 既存の指標は、洗い出しの漏れを検出できない。

**解くべきは 2 である。** 1 は実装の性質であって、なくならない。3・4・5 はすべて
2 の帰結にすぎない。

**実装が決めたことの一覧が、漏れなく、人の気づきに依存せずに手に入るなら、残りは
自動的に解ける。** 洗い出す作業がなくなれば、洗い出しの巧拙も問われない。

## 2. 主張 — 照合は機械に移り、吟味が人に残る

### 2.1 テスト設計は二つの仕事を兼ねている

現在テスト設計と呼ばれている作業には、性質の異なる二つが混ざっている。

- **照合** — 実装が要求どおりに動くかを確かめる
- **吟味** — 要求そのものが妥当かを考える

どちらもテストの仕事である。経験のある設計者は両方をこなしているし、要求の穴に
気づくことには実際の価値がある。ここを否定する意図はない。

問題は、二つが同じ工程に畳み込まれていることである。畳み込まれているために人が
全部を手でやることになり、そして工数の大半は照合に消える。

### 2.2 照合が必要なのは、翻訳があるからである

なぜ照合という仕事が存在するのか。**要求と実装が別の言葉で書かれているからである。**

従来の開発では、要求は自然言語で書かれ、設計を経て、コードになる。二回の翻訳が挟まる。
翻訳のたびに意味はずれ、ずれたかどうかは翻訳結果を読んでも分からない。照合とは、
このずれを人手で探す作業である。

Rulealize では、翻訳が一回減る。ルールセットを書けば、それがそのまま実行されるから
である。設計からコードへ翻訳する工程が存在しない。中間に置かれる成果物がないので、
そこでずれることもない。

ここで主張しているのは、**ルールセットの先にコードがない** ということだけである。
ルールセットが要求の記述として読めるかどうかは、別の問題である。現状は JSON であり、
手で書くのはエンジニアであっても骨が折れる。要求を持つ人が直接読み書きできる形にする
ことは目標であって、達成された事実ではない。§6 で限界として扱う。

残るのは、自然言語の要求からルールセットへの一回である。この翻訳は消えない。
「8 文字以上」と書くつもりで「8 文字より多い」と書いても、誰も気づかない。
ただしこの距離は、自然言語からコードまでの距離より短い。ルールセットが述べるのは
何が合法で何が起きるかであって、それをどう計算するかではないからである。

**照合の工数が大きく減るのは、機械が賢いからではない。翻訳を一回減らした基盤の上に
立っているからである。**

### 2.3 主張 — 照合は機械に移り、吟味が人に残る

翻訳が一回減り、ルールセットの先にコードがなくなった。ならば、ルールセットが何を
決めているかは、ルールセットから得られる。**状態空間を歩けば、各状態で何が合法か、
終局か、どこへ遷移するかが分かる。** それを並べたものがテスト設計である (§4)。

**照合にあたる作業は、まるごと機械に移る。**

テスト設計の工数を分解すると、こうなる。

| 工程 | 誰がやるか |
|---|---|
| どんなケースがあるかの洗い出し | 機械 |
| テストデータの用意 | 機械 |
| 期待値の決定 | 機械 |
| 機械の選び方を変える | **人** |
| 出された設計が意図どおりかを確かめる | **人** |

> **テスト設計を作る工数は機械に移る。人に残るのは、機械の選び方を変えることと、
> 出された設計が意図どおりかを確かめること——すなわち吟味である。**

ここで効いているのは、人に残る二つが **どちらも書き起こす作業ではない** ことである。
並んだものを読み、必要なら選択を差し替える。ゼロから洗い出す工程が消えている。

かつての主張は「人が介入すべきは、要求が決めきれなかった判断だけである」だった。
これは見る量を減らす主張であり、要求由来の判断と実装都合の判断を機械が仕分けられる
ことに全体重が乗っていた。**その仕分けは機械にはできない。** ある拒否が意図されたもの
か、評価の副作用かは、書いた人の頭の中にしかない。

だから量は減らさない。**全部出す。** 減るのは作る工数の方である。列挙の完全性は機械的に
保証できるが、仕分けの正しさは保証できない。主張は、保証できるものの上に置く。

### 2.4 不要にできるのは発見であり、判定ではない

この主張には当然の反論がある。設計を読んで意図との差に気づくのは人間であり、
それこそが QA の才能ではないか、と。

そのとおりである。ただし才能は二つに分かれる。

| | 発見 | 判定 |
|---|---|---|
| 内容 | どんなケースがあるかに**気づく** | それが意図どおりかを**決める** |
| 失敗したとき | 沈黙する。洗い出せなかったケースは、洗い出せなかった事実ごと消える | 一覧の上に残る。判断の対象が消えないので、後から見直せる |
| 教えられるか | 「気づけ」としか言えない | 要求の当事者に聞けば答えが出ることが多い |

**RDTD が不要にするのは発見であり、判定ではない。** 判定は残る。むしろ、そこに人を
集中させることが目的である。

決定的なのは失敗の可視性である。§1.3 で挙げた才能の三性質——再現しない、スケール
しない、退職する——が致命傷になるのは発見の側である。判定を誤っても、**そのケースは
一覧に残り続ける。** 誰かが後から読み直せる。発見の失敗にはその機会がない。

加えて、判定は多くの場合、才能ではなくドメイン知識の問題に落ちる。「一度キャンセル
した注文を再びキャンセルできるか」を決めるべきは QA ではなく、要求を持つ人である。
一覧に並んでいれば、その人に見せられる。**探し当てる必要がない。**

### 2.5 「どこまで書けば十分か」に答えが出る

「もっと詳細に要求を書けばよいのではないか」という反論がある。もっともだが、
答えられない問いが一つ残る。**どこまで書けば十分なのか。**

従来、この問いに答える手段はなかった。書き漏らしたことは、書き漏らしたという事実ごと
見えない。十分かどうかを判断できる人が「経験のある人」と呼ばれてきた。

RDTD は「ここが穴です」とは言わない。言えない。ある拒否が意図されたものか、評価の
副作用かは、書いた人の頭の中にしかないからである。

**代わりに、全部並べる。** ガードが `A AND B` なら、A と B のそれぞれが結果を決める
ケースが並ぶ。読んだ人が「A が真で B が偽のとき非合法になるのか、そこは許すつもり
だった」と気づく。気づけるのは、探し当てたからではなく、**並んでいたから** である。

これが問いへの答えになる。**一覧は有限であり、抜けなく並んでいる。だから読み切れる。**
従来は一覧そのものが存在しなかったので、読み切るという概念がなかった。十分かどうかは
経験で判断するしかなかった。いまは、読み切ったかどうかを自分で確かめられる。

### 2.6 主張が及ぶ範囲

以上の主張は Rulealize の上でのみ成立する。次の三つに依存しているからである。

- ルールセットが宣言的であり、**どの状態を読んでいるかを機械が辿れること** (§4.3.2)
- ルールセットが実行される実装そのものであり、翻訳が挟まらないこと
- 状態空間を歩く手段を基盤が持っていること

汎用言語で書かれた実装には、どれも当てはまらない。§1 で述べた問題はそこでも起きるが、
RDTD はそれを解かない。**適用範囲が狭いことは主張の一部である。**

Rulealize の上でも、RDTD から見えない領域がある。プラグインの内部である。
プラグインは C# で書かれ、その中で下される判断はルールセットの側からは読めない。

ただし、ここが才能の領域に戻るわけではない。**プラグインは単一の責務ごとに作るもの**
だからである。比較なら比較、分岐なら分岐だけを提供する。責務が一つなら、その中で
下される判断も少なく、範囲も狭い。見えない領域は残るが、小さい。

見えない領域が大きくなるのは、一つのプラグインに何でも詰め込んだときである。それは
可能だが、ルールセットで表現できるはずのものをコードに戻す行為であり、Rulealize を
使う意味そのものを失わせる。**プラグインが肥大しているなら、それは RDTD 以前の
設計の問題である。**

そしてプラグインは、案件ごとに無数に作られるルールセットとは違い、有限であり、
複数の案件に共有される。一度きちんと検証すれば、その成果は使い回される。
**無限に増える側を機械が検証し、有限で共有される側に人の検証を集中させる。**
工数が減るのは、この非対称性による。

## 3. 基盤 — Rulealize

§2 は「この主張は Rulealize の上でのみ成立する」と宣言した。本節はその根拠を示す。
Rulealize の全体像ではなく、**RDTD が必要とするものを、なぜこの基盤が持っているか**
に絞って述べる。

### 3.1 Rulealize とは何か

宣言的な JSON で書かれたルールセットをランタイムにコンパイルし、状態に入力を適用し、
**いまこの状態から合法な入力をすべて列挙し**、次の状態が指し手の側の決定でないときに
何が起こりうるかを述べ、その状態が終端かを判定する。

構成は三層である。

| 層 | 何が書かれるか | 誰が書くか |
|---|---|---|
| ルールセット (JSON) | 何が合法で、何が起きるか | いまはエンジニア。将来は要求を持つ人 |
| プラグイン (C#) | ルールセットで使える演算の語彙 | エンジニア |
| ランタイム | ルールセットの解釈と評価 | Rulealize |

重要なのは、**コアが演算を一つも持たないこと**である。真偽値すら持たない。
ルールセットに書けることは、読み込んだプラグインが提供した語彙が全てである。

リバーシのルールセットを読み込んだ実行例を挙げる。

```
Rule set: reversi@1.0.0   inputs: place, pass

    a b c d e f g h
 6  - - - - . - - -  6
 5  - - - @ O . - -  5
 4  - - . O @ - - -  4
 3  - - - . - - - -  3

 @ black 2    O white 2    turn: black    passes: 0
 legal: place(at: e6), place(at: f5), place(at: c4), place(at: d3)
```

最後の一行が RDTD にとって決定的である。**この状態で合法な入力が、すべて並んでいる。**
ホストプログラムはリバーシのルールを一行も知らない。プラグインのフォルダを読み、
ルールセットをコンパイルし、何が合法かを尋ねているだけである。

### 3.2 表現力を捨てて、列挙可能性を買う

§1 の問題は、突き詰めれば **汎用言語では判断を数え上げられない** ことに帰着する。
`if` の条件は任意の式であり、その式が何通りの結果を持つかは、一般には決定不能である。

ルールセットには、書けることの上限がある。入力には名前とパラメータ領域があり、
ガードは読み込まれた語彙の演算だけで組み立てられ、遷移は宣言される。上限を決めるのは
語彙である。語彙が細かい演算に保たれているかぎり、ルールセットは数え上げられる形に
とどまる。**書けないことが多いほど、数え上げられることが増える。**

これは新しい発想ではない。型システムは値の自由を奪って検査を可能にし、SQL は実行手順を
書く自由を奪って最適化を可能にし、正規表現は計算能力を捨てて判定の停止を保証した。
強い道具はたいてい、**表現力を捨てて保証を買っている。**

Rulealize が買ったものは、列挙可能性である。RDTD はその上でしか成立しない。

### 3.3 境界が、ルールセットを宣言的な形に保つ

§3.2 で、ルールセットに書けることの上限は語彙が決めると述べた。その上限は、守ろうと
努力して守られるものではない。**構造として強制される。**

ルールセットに書けないことは、プラグインに書くしかない。そしてプラグインに書いた
ものは、ルールセットからは語彙として——`op` の名前と引数として——現れる。任意の式が
条件の中に紛れ込む経路がない。

§1.1 のパスワードの例と比べると、差が分かる。汎用言語ではこう書かれていた。

```csharp
if (password.Length < 8) return Error.TooShort;
```

この一行には、「8」という閾値と、「`.Length` がどう数えるか」という意味論が同居して
いた。Rulealize では、前者はルールセットに書かれ、後者は比較と長さの語彙を提供する
プラグインの中にある。**同居できない。**

これが §2.6 の第一条件——どの状態を読んでいるかを機械が辿れること——を成立させている。
ルールセットのガードは常に語彙の組み合わせなので、木を降りれば `$名前` と `state.get` が
そのまま拾える。汎用言語の `if` の条件は任意の式であって、同じことはできない。

> Rulealize が強制しているのは、要求と実装を区別して書くことではない。
> **書き方の制約** である。ルールセットが宣言的な形に保たれるのは、その結果にすぎない。
> だが、テスト設計を機械的に導くには、それで足りる。

### 3.4 基盤が既に持っているもの

Ruledger は列挙器を自前で作らない。そして、**足りないものもない。**

| 機能 | Ruledger にとっての意味 |
|---|---|
| `GetValidInputs` | ある状態で合法な入力をすべて返す。**テスト設計の中身そのもの** (§4.2) |
| `GetOutcomes` | 次の状態が誰の決定でもないとき、分岐を確率つきで列挙する。偶然に委ねられた分岐も取りこぼさない |
| `CreateContext` | ルールセットから決定可能なことを事前に全て検証し、問題のある箇所を JSON ポインタで指す |
| ルールセットがデータであること | 版が付き、差分が取れる。**版をまたいだ設計の比較が成立する** |

最後の一つが §4.5 の差分を支えている。ルールセットがコードであれば、版の違いは
コードの差分にしかならない。データであれば、同じ導出を前後の版に適用して、
出てきたテスト設計どうしを比べられる。

`GetValidInputs` が返すのは、篩った結果であって篩い方ではない。どの部分式が候補を
落としたかは返らない。**それでよい。** ルールセットに無い入力は適用できないので、
落ちた理由は観測できる振る舞いに対応しない (§4.2)。テスト設計が必要とするのは、
残った側だけである。

### 3.5 基盤が潰している限界

実装を正とする道具には、原理的な限界がある。**実装が下した判断しか列挙できない。**
要求にあるのに実装が存在しない機能は、判断そのものが存在しないので列挙されない。
テストが実装から導かれるかぎり、これは避けられない。

Rulealize では、この限界が小さくなる。ルールセットが、そのまま実行されるものだから
である。「ルールセットに書いたが実装されていない」という状態は、通常の意味では
起こらない。書かれたガードも遷移も、そのまま評価される。

消えるわけではない。自然言語で述べられた要求のうち、ルールセットに書き落とされ
なかったものは、やはり見えない。§2.2 で述べた最後の一回の翻訳が、ここにも現れる。
**基盤は限界を小さくしたが、消してはいない。** §6 で限界として改めて扱う。

## 4. 仕組み — Ruledger は何をするか

### 4.1 出力はテスト設計である

読むもの。

- ルールセット
- 読み込まれたプラグインの語彙
- 粒度と出力の設定
- 差分を取る場合は、前の版の設計

出すものは **テスト設計** である。歩いて集めた状態と、その各々について観測できることの
全部。機械はすべてを埋める。人は、機械の選び方を変えたいときだけ手を入れる (§4.3)。
編集の有無にかかわらず、そのまま自動テストとして実行できる。

### 4.2 テスト設計は、観測できることでできている

ルールセットについて外から観測できることは、三つしかない。

| 単位 | 何が分かるか |
|---|---|
| 状態 | その状態で合法な入力の集合。一つの入力とは、名前と引数と、**それが誰の手か** である |
| 状態 | 終局かどうかと、終局なら `Result` |
| 状態 × 合法な入力 | 適用した後の状態 |

テスト設計は、この三つを状態ごとに並べたものである。それ以外のことを書いても、
確かめようがない。

`reversi.json` に対する出力は、次の形になる。

```
reversi@1.0.0   inputs: place, pass

状態 #0   初期状態
  合法    place(at: c4)  place(at: d3)  place(at: e6)  place(at: f5)     4 / 65
  終局    継続
  state   { "board": { "d5": "black", "e5": "white", "d4": "white", "e4": "black" },
            "turn": "black", "passes": 0 }

状態 #1   #0 + place(at: c4)
  合法    place(at: c3)  place(at: c5)  place(at: e3)                    3 / 65
  終局    継続
  state   { "board": { "d5": "black", "e5": "white", "c4": "black", "d4": "black",
            "e4": "black" }, "turn": "white", "passes": 0 }
```

`65` は候補の全数である。`place` の 64 通りと `pass` の 1 通り。

**合法な入力が並んでいれば、残りが非合法であることは、そこに書かれている。**
「d4 は埋まっているので置けない」という項目は要らない。d4 が一覧にないことが、
それを述べている。読む人は四つを見て「この四つで合っている」と確かめられる。
五つ目があるはずだと思えば、それが食い違いである。

> **非合法の理由を書き出す必要はない。** 書き出しても実行できない——ルールセットに
> 無い入力は適用できないからである——し、読む材料としても、合法な集合の裏返しでしか
> ない。「置けない場所に置いたら断る」という振る舞いが要るなら、それはルールであり、
> ルールセットに書けば入力として現れ、普通に観測できるようになる。

### 4.3 何を網羅し、どう歩くか

網羅の対象も、観測できることに限られる。

| 網羅の単位 | 決め方 |
|---|---|
| 入力とパラメータ値の組 | `place(at: a1)` が合法になる状態はあるか |
| 終局と継続 | 終局に至る状態と、至らない状態 |
| `Result` の分岐 | `terminal.result` の分岐を読めば、何通りあるかが出る |

三つ目はルールセットから静的に読める。一つ目と二つ目は、歩いて確かめるしかない。

**「何通りのうち何通り」と言えるとはかぎらない。** パラメータ領域は状態を読む定義で
よいので (チェスは指し手の生成そのもの)、候補の数は状態ごとに変わる。リバーシの 65 が
一定なのは、たまたまその領域が盤面の中身に依らないからである。

### 4.3.1 歩き方に要るのは、再現できることだけ

状態を得るのは機械である。合法な入力を得て、適用して次の状態を得て、終局かを判定する。
**各状態で合法な入力を全部たどり、一本の経路を終局まで歩き切ってから戻る。**

無作為に一つ選ぶのは枝を捨てているだけで、何も保証しない。浅い順に広げるのは、一局も
打ち終えないまま序盤ばかりを集める。**終局を観測したければ、終局まで歩くしかない。**

リバーシで実測すると差が出る。同じ 3,000 状態の予算で、浅い順に広げると深さ 5 までしか
進まず、終局は 0 件、`result` は一つも観測されない。終局まで歩き切る順なら深さ 62 に達し、
終局 849 件、`result` は black・white・draw の三種すべてが出る
([verification.md](verification.md))。

**思想が求めるのは、ここまでである。** この骨格の中にはまだ選択肢がある——歩き切った
あとどこまで戻るか、同じ状態に二度着いたときの判定をいつ行うか。**どれを選んでも
§4.5 の差分と §6.7 の持ち越しは成立する。両版を同じ設定で歩くかぎり、同じ状態を同じ順で
訪れるからである** (論証であって、実測したのは既定の設定だけである)。要求は一つで足りる。

> **歩き方は再現可能でなければならない。**

同じルールセットからは必ず同じ状態を同じ順で訪れる、ということである。乱数も、種も、
入り込まない。**それ以外は設定であり、設計とともに記録される** (§4.5)。

歩き方の選択肢は実測で並べた。**どれかが上手いのではない。** 網羅の対象が互いに
反対を向いているだけで、選ぶ根拠は思想の側にない。
だから思想は選ばない。

### 4.3.2 同じ状態かどうかは、観測に影響する状態だけで決める

歩いた先が既に見た状態なら、その先も見ている。二度歩く必要はない。

問題は「同じ」の定義である。状態を丸ごと比べると、**観測に関係のない違いで別物になる。**
監査ログや操作履歴を状態に持つルールセットは珍しくない。そこに一行増えるだけで状態は
変わるので、同じ割り当てに戻っていても別の状態と見なされる。

履歴を状態に持てない、という制約を書き手に課すべきではない。**Ruledger の側で扱う。**

同定に使う状態は、機械的に決まる。

```
観測点  = 各入力のガード / パラメータ領域 / actor / terminal.when / terminal.result
観測    ← 観測点から (定義をたどって) 読まれる状態パス
繰り返し:
    観測 ← 観測 ∪ { 観測に属する状態へ書き込む効果が読んでいる状態 }
    変化がなくなるまで
同定に使うのは観測だけ。残りは潰す
```

状態への参照は `$名前` と `state.get` の二つの形でしか現れない。プラグインは状態を直接
読めず、受け取るのは評価済みの引数だけだからである (§3.1)。**この走査に取り逃がす経路は
ない。語彙がいくつ増えても変わらない。**

不動点が要るのは、間接の影響があるからである。履歴をどのガードも読んでいなくても、
観測される状態を書き換える効果がそれを読んでいれば、履歴は観測に影響する。

**効くのは歩行そのものである。** 潰さなくても歩けはするが、履歴を持つルールセットでは
**二度と同じ状態に戻らない。** 実測では合流が一件も起きず、二つある `result` の片方が
予算内で一度も観測されなかった。潰すのは、歩行が戻れるようにするためである。

**同定がこれ以外に要る場所は無い。** 差分と持ち越しは状態の名前——`#1 = #0 + place(at: c4)`
という来かた——で引く (§6.7)。項目が一つ増えれば鍵が全部変わる同定をそこに使うと、振る舞いが
何も変わっていない変更で編集が全部落ちるからである。実測は [verification.md](verification.md)。

### 4.3.3 予算と、届かなかったもの

歩き尽くせるルールセットは少ない。リバーシの到達可能な状態は 10²⁸ 規模である。
どこかで打ち切ることになる。

予算には向きが二つある。

| | 何のための予算か |
|---|---|
| **抑える側** | 入力が 9999 通りあっても、9999 件のテストケースに意味はない。だから絞る |
| **回す側** | 訪れる状態の数に上限を置く。歩き尽くせないから |

打ち切ったなら、**何に届かなかったかを表に出す。** チェスを 20,000 状態で歩くと
`result` は `draw` しか出ない。予算を 200,000 に上げても変わらない。「詰みが起こらない」
のではなく「この予算では届かなかった」である。両者を混同しない。

**届かなかったものは、歩き方の設定にも依る** (§4.3.1)。同じ予算でも、設定が違えば
観測できる `result` が違う。設定は記録されるので揺れないが、
**予算内で観測できた `result` の集合を「ありうる `result` の集合」と読んではいけない。**

届かないことが、ルールセットの側を指すこともある。将棋の `terminal.when` は
「指せる手がない」ことだけで、チェスの `idle >= 100` に当たるものがない。
**終局が保証されていない。** 実際の将棋には千日手の規定があり、それが書かれていない。

穴を指摘できること自体は、Ruledger の失敗ではなく Ruledger が拾ったものである (§2.5)。

### 4.3.4 人が手を入れるとき

機械がすべての状態と入力を選ぶが、選び方が気に入らないことはある。

```
状態 #1   #0 + place(at: c4)          ← d3 を指したときで確かめたい
```

差し替えれば、そこから先は機械が算出し直す。合法な入力の集合も、終局の判定も、
遷移先の状態も、すべてランタイムが答える。**人が書くのは選択であって、観測結果では
ない。** 観測結果を手で書けば、そこが唯一の誤りうる箇所になる。書かせない。

> **「人が介入すべき箇所」とは、機械の選び方を変えたいときだけである。**
> 機械が選べないのではない。機械が選んだものを、人が上書きできる。

算出し直すのは、その状態から先の全部である。だから **編集は上から順に積むことになる。**
一件目がそれより後の状態を作り直すので、まとめて付けることはできない (§6.7)。

### 4.4 トートロジーは条件であって、欠陥ではない

ルールセットから導いた設計は、ルールセットと同義である。同じ版に対して実行すれば必ず
通る。何も証明しない。

これは欠陥ではない。**オラクルは人の意図であり、システムの外にある。**

むしろ逆で、同義だからこそ信用できる。機械が気を利かせて解釈を加えたら、それは
「ルールセットが実際に何を言っているか」ではなくなる。**解釈がゼロであることが、
読み合わせ資料としての忠実さの保証である。**

§2.2 で、自然言語の要求からルールセットへの翻訳だけは消えないと述べた。「8 文字以上」の
つもりで「8 文字より多い」と書いても誰も気づかない、と。**Ruledger が気づかせるのはそこ
である。** そう書けば、設計に「8 文字ちょうどは非合法」と出る。読めば分かる。

合っていれば何もしない。違っていれば **ルールセットを直す。**

### 4.5 差分 — 版をまたぐと回帰検出になる

編集済みの設計はリポジトリにコミットする。次に出力したときの差分が、変更の影響である。

リバーシの `terminal.result` で、勝ちの割り当てだけを入れ替えたときの差分。

```
reversi.json  ->  reversi-swapped.json   予算 3000 状態
  共通の状態      3000
  うち観測が変化  844
  片方だけの状態  前 0  /  後 0

  状態 #60 = #59 + place(at: h1)
  -   終局  終了 black
  +   終局  終了 white
  ... ほか 843 件
```

**状態空間は完全に一致している。** 合法な入力は一件も変わっていない。変わったのは終局
844 件の勝敗だけで、それはまさに書き換えた箇所である。

同じルールセットで、置ける条件を「2 枚以上挟めるとき」に変えると、こうなる。

```
reversi.json  ->  reversi-strict.json   予算 3000 状態
  共通の状態      1
  うち観測が変化  1
  片方だけの状態  前 2999  /  後 2

  状態 #0
  -   合法  place(at: c4) place(at: d3) place(at: e6) place(at: f5)
  +   合法  pass
```

初期状態のほかは何も共通していない。リバーシの初期配置はどの手も 1 枚しか挟めないので、
置ける手が消え、`pass` だけが残る。**一行変えただけでゲームが始まらなくなったことが、
共通の状態が 1 件しかないことに出ている。**

読むのは変わった行だけである。そして **「この一行を変えたら、どの状態で何が合法で
なくなり、どこへ波及したか」が機械的に出る。** 影響範囲の見積もりは、これまで才能で
行われていた。

**差分は変更の大きさに比例する。** 勝敗の割り当てを変えれば勝敗だけが変わり、置ける
条件を変えれば状態空間ごと変わる。

差分は揺れない。**歩き方に無作為な要素がないからである。** 合法な入力は宣言された順に
たどり、経路は終局まで歩き切ってから戻る。同じルールセットからは、必ず同じ順で同じ状態を
訪れる。乱数も、種も、探索の戦略も入り込まない。

観測そのものも決定的である。ある状態で何が合法かも、終局かどうかも、遷移先も、ランタイムが
一意に答える。

したがって、差分に現れるものは変更に由来する。**設定を変えないかぎり。** 予算も
歩き方も設定であり、設計とともに記録される (§4.3.1)。**両版を同じ設定で歩くかぎり、
差分も持ち越しも成り立つ。**

**承認記録は持たない。** 承認とは設計をコミットしたことであり、失効とは差分が出たこと
である。既存の道具がすでにやっていることを、作り直す必要はない。

## 5. 開発体験

§4 は機械の側から述べた。ここでは人の側から述べる。

### 5.1 一回の変更の流れ

ルールセットを変える。Ruledger を走らせる。差分を読む。それだけである。

リバーシの規則を「2 枚以上挟めるときだけ置ける」に変えるとする。`canPlace` を直して、
差分を出す。

```
状態 #0   初期状態
-  合法    place(at: c4)  place(at: d3)  place(at: e6)  place(at: f5)     4 / 65
+  合法    pass                                                           1 / 65
   終局    継続

状態 #1
-  #0 + place(at: c4)
-  合法    place(at: c3)  place(at: c5)  place(at: e3)                    3 / 65
+  #0 + pass
+  合法    pass                                                           1 / 65
   終局    継続
```

読んで、意図どおりなら次へ行く。違っていればルールセットに戻る。この例なら、初期盤面で
打てる手が消えて `pass` だけになっている。リバーシの初期配置はどの手も 1 枚しか挟めない
ので、「2 枚以上」は初期配置と両立しない。**一行変えただけでゲームが始まらなくなった
ことが、最初の二状態で分かる。**

ここで **起きていないこと** を挙げるほうが早い。テストケースを一件も書いていない。
テストデータを用意していない。期待値を計算していない。どこに影響するかを考えてもいない。
`pass` にも波及することを、思い出してもいない。

### 5.2 影響は、探しに行かず、向こうから来る

従来、ルールを一つ変えたあとの仕事は「どこに影響するか」を考えることだった。
`canPlace` は `place` のガードで使われ、`hasAnyMove` を経由して `pass` のガードでも
使われている。気づけば両方を確認する。気づかなければ片方だけ確認して終わる。
そして気づかなかったことは、誰にも分からない。

Ruledger の下では、この工程がない。波及は差分に現れる。**探す作業がないので、探し損ねる
こともない。**

これが §1.2 で述べた二択——全部読むか、勘で選ぶか——に対する三つ目の答えである。
全部読む必要はなく、勘で選ぶ必要もない。変わったものだけが並んでいる。

### 5.3 差分の大きさが、そのまま変更の大きさである

一行直して差分が三行なら、小さい変更である。一行直して差分が二百行なら、
**それは小さい変更ではなかった。**

従来、この判断は書いた人の実感に頼っていた。「ちょっと直しただけ」が事故になるのは、
実感と実際がずれるからである。差分はずれない。

読むのが苦痛なほど差分が大きいなら、原因は二つのどちらかである。変更が本当に大きいか、
粒度を上げすぎているか。前者なら変更を分けるべきで、後者なら粒度を下げればよい。
どちらなのかは、**粒度を下げて出し直せば分かる。** それで小さくなるなら粒度の問題で
あり、小さくならないなら変更の問題である。

### 5.4 代表値を変えたくなったとき

機械はすべての具体値を埋めるが、選び方が気に入らないことはある (§4.3)。

```
状態 #1   #0 + place(at: c4)          ← d3 を指したときで確かめたい
```

差し替えれば、そこから先は機械が算出し直す。合法な入力の集合も、終局の判定も、遷移先も、
すべてランタイムが答える。**人が書くのは選択であって、観測結果ではない。**
観測結果を手で書けば、そこが唯一の誤りうる箇所になる。書かせない。

編集した設計はリポジトリに入る。ルールセットを変えて出し直しても、**選択は残る。**
編集が指しているのは状態と入力であって、ルールセットの構造ではないからである。
残る量は変更の大きさに比例し、失われたものは表に出る。条件と、残っている穴は §6.7。

### 5.5 いま誰が使えるか

正直に書いておく。**この体験ができるのは、いまのところルールセットを読める人だけで
ある。**

§6.4 で述べるとおり、ルールセットは JSON であり、手で書くのはエンジニアであっても
骨が折れる。「要求を持つ人が設計を読んで意図と照らす」という像は、まだ前提が整って
いない。

したがって当面の利用者は、ルールセットを書く人と、その変更をレビューする人である。
その二人には、ここに書いた体験がそのまま成立する。要求を持つ人に届けるには視覚化が
要る。それは次の課題であって、この思想が達成済みだと主張するものではない。

**これは対象を狭めているのではなく、段を置いている。** 基盤が新しいので、ルールセットを
読める人はまだほとんどいない。**読めることを条件にしたのではなく、最初の段がそこにある
というだけである。** 向かう先は §6.4 の像——要求を持つ人がルールを組み立て、出てきた設計を
読んで意図と照らす——であり、視覚化はそこへ上がるための次の段である。

条件だと読まれれば、読む人のいない思想になる。**段を一つずつ上がることと、届く範囲を
ここで確定させることは、別である。**

## 6. 限界と適用範囲

RDTD は何も直さない。問題を指摘もしない。ルールセットが決めたことを並べるだけである。
それが何を意味するかを、ここで正確に述べる。

### 6.1 見えないもの

**自然言語の要求と、ルールセットの間。** §2.2 で述べた最後の一回の翻訳である。
RDTD が読むのはルールセットだけであり、書いた人が何を意図したかは読めない。
「8 文字以上」のつもりで「8 文字より多い」と書けば、設計に「8 文字ちょうどは非合法」と
現れる。だが、それが誤りかどうかを言うのは人である。

**実装されなかった要求。** 列挙できるのは、ルールセットが決めたことだけである。要求に
あるのにルールセットに書かれていない機能は、そもそも存在しないので列挙されない。
実装を正とする道具である以上、原理的に避けられない。

Rulealize ではこの穴が小さい (§3.5)。ルールセットがそのまま実行されるので、「書いたが
動いていない」という乖離が起きにくいからである。だが「書かなかった」は残る。
**書かれなかったものを見つける道具は、Ruledger ではない。**

**プラグインの内部。** プラグインは C# で書かれ、その中で下される判断はルールセットの
側からは読めない (§2.6)。単一責務に保たれていれば範囲は小さいが、ゼロではない。

### 6.2 判定しないもの

**要求由来か、実装都合かの区別。** ある拒否が意図されたものか、評価の副作用かは、
書いた人の頭の中にしかない。機械には判定できない。だから仕分けはせず、全部並べる
(§2.3)。

**正しさ。** オラクルは人の意図であり、システムの外にある。ルールセットから導いた設計を
同じルールセットに当てれば、必ず通る (§4.4)。Ruledger が出すのは「こう決まっている」で
あって、「これでよい」ではない。

**吟味されたかどうか。** 設計を読んだかどうかは、本人にしか分からない。読まずに通すことは
できるし、それを検出する手段はない。§1.4 でカバレッジを批判したのは、数字が満点でも
中身が確かめられていないことがあるからだった。Ruledger は代わりの数字を出さないので同じ
誤用は起こらないが、**吟味を強制することもできない。**

### 6.3 基盤に依存していること

§2.6 の三条件——ルールセットが宣言的であること、その先にコードがないこと、状態空間を
歩けること——は Rulealize が満たしている。汎用言語は満たさない。
**RDTD は汎用言語に適用しない。**

Rulealize の上でも、依存が一つ残る。**語彙の粒度である。** ルールセットが数え上げられる
形にとどまるのは、プラグインが細かい演算を提供しているかぎりである (§3.2)。一つの
プラグインに何でも詰め込めば、ガードは `op` 一つになり、論理構造は消える。そのとき
RDTD は何も導けない。

これは RDTD が防げることではない。防ぐのは Rulealize の設計であり、守るのはプラグインを
書く人である。

### 6.4 まだできていないこと

ここまでは原理的な限界である。次の一つは違う。**まだできていない、というだけである。**

ルールセットは JSON であり、手で書くのはエンジニアであっても骨が折れる。「要求を持つ人が
ルールを組み立て、出てきた設計を読んで意図と照らす」という像は、その前提が整っていない。
**読み書きできない人に、読み合わせはできない。**

これは Ruledger だけの問題ではなく、Rulealize と Ruledger の両方にかかる未達である。視覚化と
編集の手段が要る。v1 には含まれない。

### 6.5 何に対して実行するか

先に正しておくべきことがある。**Ruledger はすでにルールセットを実行している。** 期待値を
算出するには、その状態にその入力を適用して結果を見るしかない。設計を出す作業と実行する
作業は、同じことの言い換えである。

線は「実行するかしないか」ではなく、**何に対して実行するか** に引かれる。

| 当てる先 | 何が分かるか |
|---|---|
| 同じ版のルールセット | **何も分からない。** 必ず通る (§4.4) |
| 前の版の設計 × 新しい版のルールセット | 期待値が変わったものが出る。**これが §4.5 の差分そのものである** |
| ルールセット以外 (ホスト、画面、永続化、外部連携) | いまは見えない。**ルールセットに書かれていないからである** |

二行目が重要である。**実行と差分は別の機能ではない。** 前の版の設計を新しい版に当てて
期待値を照合することと、前後の設計を突き合わせて差分を出すことは、同じ操作を別の側から
述べたものにすぎない。回帰の検出は、差分機能が最初から持っている性質である。

三行目が、現在の範囲の外側である。ルールセットが「この状態でこの入力は合法」と述べて
いても、それを使う画面が実際にボタンを押させるかどうかは別の話であり、いまの Ruledger は
答えを持たない。

**ただしこれは原理的な壁ではない。** 見えないのは、ルールセットに書かれていないから
である。ルールセットに書けることは、読み込んだ語彙が決める (§3.2)。画面の状態や遷移を
述べる語彙があれば、それもルールセットに書かれ、そのぶんテスト設計に現れる。
Rulealize 自身、`GetValidInputs` の用途として「画面で押せるボタンの集合」を挙げている。
前提はすでに置かれている。

つまり **Ruledger が届く範囲は、ルールセットが表現している範囲と一致する。** 広げるのに
Ruledger を変える必要はない。語彙を足せばよい。そのとき、画面を含めたソフトウェア全体を
通した検証が、同じ仕組みで成立する。

**v1 はそこまでやらない。** だが、できないから外しているのではなく、先にやることが
あるから外している。§6.1 から §6.4 に挙げたものとは、性質が違う。

### 6.6 v1 が受け持つ範囲

| | v1 |
|---|---|
| テスト設計を導き、具体値と期待値を埋める | 含む |
| 前の版の設計を新しい版に当て、変わったものを出す | 含む |
| 人が入れた編集を、ルールセットを変えたあとへ持ち越す | 含む (§6.7)。差分と同じ名前で足りる |
| ルールセット以外の検証 | **含まない。** ただし原理的な限界ではない (§6.5) |
| ルールセットの視覚化と編集 | **含まない** (§6.4) |
| 承認の記録 | **持たない** (§4.5) |

既存のテスト実行環境が読める形で出すかどうかは、出力形式の問題である。思想が決めること
ではなく、実装の段で決めればよい。

### 6.7 編集の持ち越し — 状態に貼る

人が代表値を書き換えたあと、ルールセットを変えて設計を出し直すと、その選択はどうなるか。
機械が既定どおりに選び直せば、書き換えは消える。残すには、**出し直した設計のどれが前の
どれと同じものなのかを、同定する必要がある。**

#### 編集はルールセットを指していない

人が書くのは選択だけである (§4.3.4)。

```
状態 #1   #0 + place(at: c4)          ← d3 を指したときで確かめたい
```

この一件が持っている情報は二つしかない。**どの状態で**、**どの入力を選ぶか。** 前者は
状態そのものであり、後者は `place(at: d3)` という入力の名前と引数である。**どちらにも
ルールセットの構造は現れない。**

そして状態を版をまたいで同定する仕掛けは、すでにある。**出力が状態を呼んでいる名前が
それである。** `#1 = #0 + place(at: c4)` は初期状態からの来かたであり、§4.5 の差分が
使っているものと同じである。**新しい機構は要らない。** 編集はその名前で引く。

#### 観測結果を変えない変更では、一件も失われない

予算 3,000 状態、編集 20 件で実測した (将棋だけ 300 状態・10 件。
[verification.md](verification.md))。

| 変更 | 持ち越せた | 入力が非合法 | 届かなかった |
|---|---|---|---|
| (対照) 同じ版 | **20** | 0 | 0 |
| リバーシ: 勝ちの割り当てを入れ替え | **20** | 0 | 0 |
| リバーシ: 定義名を変え、`logic.and` の引数を並べ替え | **20** | 0 | 0 |
| リバーシ: 置ける条件を「2 枚以上挟めるとき」に | 0 | 1 | 19 (状態が消えた) |
| roster: `terminal.result` の then/else を入れ替え | **20** | 0 | 0 |
| roster: 上級者しか入れないことにする | 3 | 1 | 16 |
| チェス: 詰みの勝敗を入れ替え | **20** | 0 | 0 |
| チェス: ポーンの 2 マス進みを禁止 | 1 | 1 | 18 |
| 将棋: 勝敗を入れ替え | **10** | 0 | 0 |
| 将棋: 歩を打てないことにする | **9** | 1 | 0 |

**観測結果を変えない変更では、一件も失われない。** 勝敗の割り当てをどう入れ替えても
20/20 である。到達可能な状態が動いていないからで、**966 行のチェスでも、業務ドメインの
roster でも同じである。**

**失われ方は三通りある。** 状態そのものが消えたか、選んだ入力が非合法になったか、
**上の編集が落ちて歩く順が変わり、足場ごと消えたか** である。三つ目が一番多い。
チェスの 1 / 1 / 18 がそれで、直接落ちたのは一件、残る 18 件は巻き添えである
(後述「編集は上から順に積む」)。

**差分の大きさとは対応しない。** 将棋で歩打ちを禁じると 300 状態のうち 274 で観測が
変わるのに 9/10 残り、チェスでポーンの 2 マス進みを禁じると 3,000 のうち 151 しか
変わらないのに 1/20 しか残らない。差分は合法な入力の集合が変わったかを数え、持ち越しは
編集が選んだ **その一つ** がまだ合法かを見る。別の量である。

チェスの一行目は、持ち越しと差分が別であることをもう一方から示している。この予算では
詰みに届かないので、詰んだときの勝敗を書き換えても **差分は 0 行である。** それでも
持ち越しは 20/20 になる。**差分が空でも編集の足場は残る。**

三行目が、旧稿の恐れていた場合である。定義の名前を変え、`logic.and` の引数を並べ替えて
も、一件も失われない。状態も入力の名前も変わっていないからである。**「内容で同定する」
案が落ちた理由は、状態で同定するかぎり当たらない。**

#### 穴だったのは、状態の中身で引いていたことである

状態に項目が一つ増えれば、中身で作った鍵はすべて変わる。手数を状態に足して `terminal` に
それを読ませた版で実測すると、**振る舞いは一つも変わらないのに 20 件全部が失われた。**
予算内では手数が閾値に届かない。合法な入力も終局も遷移先も、一つも動いていない。

これが「一行直すたびに人の書き換えが全部消える」の、現実に起きる唯一の形だった。
**旧稿はこれを避けられないと書いていた。避けられない理由は一つしかなく、それは鍵を状態の
中身で作っていたことである。**

**名前で引けば消える。** 状態の名前は初期状態からの来かたであり、項目が増えても
`#0 + place(at: c4)` は `#0 + place(at: c4)` のままである。同じ変更で測り直した
(Ruledger、[verification.md](verification.md))。**状態の中身は 3,000 件すべて別物になるのに、
20 件とも残る。** 差分のほうは共通 2,999 件で、合法な入力も終局も一件も動かない。食い違う
2 件は予算の際で着地先が変わったもので、これは合流の位置が動いたのであって規則が動いたの
ではない。

**その区別は道具が出す。** 同定に使う項目が両版で違うことは §4.3.2 の走査で機械的に分かる
ので、差分がそれを述べる。読む人は「この差分のいくらかは歩き方の側である」と知った上で読む。
**黙って既定値に戻ることはない。**

編集が失われるのは、その来かたが歩かれなくなったときだけである。それは「予算内で届かなかった」
として既に表に出る (§4.3.3)。**鍵を潰し合わせる工夫も、候補を並べて人に選ばせる仕掛けも
要らない。** 中身で引いていたころは要った——両方の版に在る項目だけで引き直す案を検討し、
別々の状態が同じ鍵に潰れること (3,000 件中 206 件が 103 個の鍵に)、潰れた鍵に貼った一件の
編集が **1,001 個の状態に当たり、そのすべてで歩く順を変える** ことまで実測してある。
**その実測は、中身で引くのをやめる理由のほうに使った** (§4.4)。

#### 編集は上から順に積む

編集は状態に貼るので互いに独立に書けるが、**効き目は独立ではない。** 一件目が歩く順序を
変えるので、それより後に現れる状態は作り直される。

編集していない設計から 20 件まとめて取り、同じ版に当てると **1 件しか成立しない。**
一件ずつ、前の編集を織り込んだ設計から取れば 20 件とも成立する。予算を 3,000 から
20,000 に上げても変わらない。

これは §4.3.4 が「そこから先は機械が算出し直す」と述べたことの帰結である。設計を上から
読んで気になったところを直す、という読み方とは一致している。

#### 粒度を変えても壊れない

§5.3 は「差分が読めないほど大きいなら粒度を下げて出し直せ」と述べた。**そのとき編集が
消えては困る。** 同じ版のまま予算だけを変えて測った。予算 1,000 で作った編集を 3,000 で
出し直しても、3,000 で作ったものを 100 で出し直しても、**20 件とも残る**
([verification.md](verification.md))。

訪問順は予算に依存しないので、**予算を下げることは歩行を後ろから切ることでしかない。**
前から n 件は、予算をいくつにしても同じ n 件である。落ちるのは切った先に貼られた編集
だけで、それは「予算内で届かなかった」として表に出る (§4.3.3)。

#### 変わらない原則

**持ち越せなかったことは、隠さない。** 前の選択が失われたなら、そう表示する。黙って
既定値に戻すことはしない。届かなかった編集については、状態が消えたのか予算内で届かな
かったのかを分ける (§4.3.3)。§4.5 で述べた差分の原則と同じである。

## 7. 既存手法との位置づけ

RDTD は新しい考え方ではない。既存の手法が個別に持っていた性質を、制約された基盤の上で
組み直したものである。どれに近く、どこが違うかを述べる。

### 7.1 Approval Testing — 承認の粒度が違う

最も近い。Approval Testing は実行結果を記録し、人が一度承認し、以降はそれとの差分を
見る。実装を正とする点も、差分で回帰を見る点も、RDTD と同じである。

違うのは、分解されているかどうかである。承認の対象は出力の塊であって、その中でどの
判断がどう効いたかは見えない。出力が変われば差分は出るが、**なぜ変わったかは人が
読み解く。**

差は二つある。**状態ごとに完全であること** と、**状態が選ばれていること** である。

Approval Testing が記録するのは、実際に走った一本の道筋である。RDTD は訪れた各状態で
合法な入力を **すべて** 書き出す。指した手だけでなく、指せた手の全部が残る。だから差分は
「この状態で打てる手が四つから三つに減った」という形になり、走らせ方に依存しない。

そして訪れる状態は、走った順ではなく網羅の基準で選ばれる (§4.3)。Approval Testing は
記録した道筋の外を知らない。

**近い。** 近いことは弱点ではない。実装を正として差分で回帰を見るという骨格は、
すでに枯れている。

### 7.2 Property-based testing — オラクルの出どころが違う

QuickCheck 以来の系統では、人が性質を書き、機械が入力を生成する。「リストを二度反転
すれば元に戻る」と人が書けば、あとは機械が試す。

オラクルは人が **書く**。RDTD では、人は **読む**。機械が並べたものを見て、意図と違う
ものに気づく。書ける性質には限りがあるが、読める一覧に上限はない。

両者は競合しない。むしろ、並んだ一覧を見て「ここは性質として書けるな」と気づくことは
ある。**一覧は、性質を書く前段にもなる。**

### 7.3 Model-based testing — モデルが二重にならない

モデルベーステストでは、人が抽象モデルを書き、そこからテストを導き、実装に当てる。
導出が機械的である点は RDTD と同じである。

問題は、モデルと実装が別物であることだった。モデルが正しくても実装が違えば意味がなく、
実装を直してモデルを直し忘れれば、モデルは嘘になる。**二重管理である。**

Rulealize ではルールセットが実行されるものそのものなので、この二重化が起きない (§2.2)。
代わりに失うものもある。モデルが独立していないので、**モデルと実装を突き合わせる検査が
できない。** RDTD が原理的にトートロジーなのは、これと同じことである (§4.4)。
二重管理を捨てた対価として、独立した照合を失っている。

### 7.4 記号実行 — 同じことを、安く

条件式を集め、それを満たす入力を逆算する。**到達可能な状態を機械に挙げさせる** という
点で、RDTD と同じ発想である。

汎用言語での記号実行は難しい。経路が爆発し、制約が解けず、ライブラリ呼び出しの先で
情報が途切れる。RDTD が同じことを安くできるのは、賢いからではない。**言語が制約されて
いるからである。** ガードは語彙の組み合わせでしかなく、パラメータ領域は宣言されており、
状態はランタイムが歩ける。

§3.2 で述べた取引の内訳が、ここに出ている。**捨てた表現力の対価として得たものが、
これである。**

### 7.5 Mutation testing — 測る対象が違う

カバレッジの弱さへの答えとして、よく挙がる。実装を少しずつ書き換えて、テストが気づくかを
見る。気づかなければ、そのテストは弱い。

測っているのは **既存のテストの強さ** である。テストが一件も書かれていなければ、測る
ものがない。§1.4 で述べた問題——洗い出しの漏れ——には届かない。**書かれなかったテストは、
変異させても現れない。**

RDTD は逆側にいる。強さを測るのではなく、ケースを導く。両立する。Ruledger が出した設計を
実行可能にしたあと、その強さを mutation testing で測ることはできる。

### 7.6 借りている考え方

新しく作らずに済むものがある。

- **MC/DC** (改良条件判定カバレッジ)。これは **被覆基準** であって、テストケースの
  生成規則ではない。「各条件が独立に結果を決める場合を通れ」と述べるだけで、何を
  assert するかは言わない。RDTD でも同じ位置にある。ガードの構造は、どの状態を
  訪れるべきかの手がかりであって、出力ではない (§4.3)。
- **組み合わせテスト** (pairwise, n-wise)。粒度を上げたときの爆発を抑える方法として、
  既存の被覆配列の理論がそのまま使える。粒度の設定はここに接続する余地がある。

どちらも枯れた理論であり、作り直す理由がない。

### 7.7 一覧

| 手法 | 実装を正とするか | オラクルは誰か | RDTD との差 |
|---|---|---|---|
| カバレッジ | — | — | 書かれなかったテストを見ない (§1.4) |
| Approval Testing | する | 人が一括で承認 | 承認の粒度。RDTD は判断ごとに分解する |
| Property-based | しない | 人が性質を書く | オラクルを書くか、読むか |
| Model-based | しない | 独立したモデル | 二重管理がない代わりに、独立した照合も失う |
| Mutation testing | する | 既存のテスト | テストの強さを測る。ケースを導きはしない |
| 記号実行 | する | — | 同じ導出を、制約された言語の上で安く行う |

RDTD に固有のものは一つしかない。**制約された基盤の上でこれらを組み合わせると、
人が書き起こす工程が消える。** 個々の要素は、どれも既にあったものである。

## 付録 A. AI との関係

本文で AI に触れなかったのは、思想が AI 以前から成立しているからである。だが、AI で
実装する開発が広がったことで、この問題は見えやすくなった。関係を短く述べる。

### A.1 AI は問題を作っていない

§1 で述べた構造——実装は要求より多くを決め、その一覧はどこにも存在しない——は、人が
コードを書いていた時代から変わらない。AI が新しい問題を作ったわけではない。

変えたのは、**気づく機会** である。

従来、コードを書く行為は強制的な仕様の詰め作業だった。`if` の条件を書くには、境界を
どちらに倒すか決めるしかない。その「決めた瞬間」が書いた人の頭に残り、テスト設計の
入力になっていた。仕様書に書かれていないケースを思いつけたのは、実装中に迷った記憶が
あったからである。

AI に実装させても、判断は同じ回数だけ発生する。ただ、誰の頭にも残らない。

### A.2 これは解くべき問題の一部でしかない

記憶が失われることを問題として述べると、「では人が書けばよい」という結論になる。
そうではない。

**記憶に頼っていたこと自体が、元々の誤りだった。** 人が書いていた時代も、思い出せたか
どうかで品質が決まっていた。疲れていれば思い出せず、辞めれば持ち出される。§1.3 で
述べた三性質は、記憶に頼る仕組みの性質である。

AI はその誤りを見えやすくしただけである。**解くべきものは、AI の前後で変わらない。**

### A.3 テストも AI に書かせると、漏れが系統的になる

一点、AI に固有の影響がある。同じモデルが同じ文脈で実装とテストを書くと、テストは仕様
ではなく **実装の前提を検証する**。仕様を誤解していれば、その誤解ごとテストが通る。

従来のチームには偶然の多様性があった。実装者とテスト設計者が別人で、仕様書の読み方が
微妙に違い、そのズレ自体が検出器として機能していた。

結果、漏れの性質が変わる。

| | 人が書いた場合 | AI が書いた場合 |
|---|---|---|
| 分布 | ランダム | 系統的 |
| 場所 | 退屈な箇所に散らばる | 同じ種類が全体に一様に抜ける |
| 見つけ方 | 抜き取りで当たる | 抜き取りでは当たらない |

RDTD はこれを踏まない。**オラクルが機械の中にないからである。** 並べるのは機械だが、
意図と照らすのは人である (§4.4)。機械が意図を推測する工程がないので、推測を誤ることも
ない。

### A.4 AI が役に立つところ

逆に、AI が実務的な助けになる箇所がある。**ルールセットを書くことである。**

§6.4 で述べたとおり、JSON を手で書くのは骨が折れる。AI に書かせれば速い。そして
書かせたものが実際に何を決めたのかは、Ruledger が並べる。**書くのは AI、並べるのは機械、
確かめるのは人** という分担が成立する。

これは思想の前提ではない。視覚化と編集の手段が整うまでの回避策である。
だが、有効ではある。
